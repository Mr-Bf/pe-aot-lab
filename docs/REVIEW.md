# 方案 B 的反证审查与继续投入条件

审查日期为 2026 年 10 月 27 日。本次审查针对高性能的 Windows x86-64 PE 到 Apple Silicon ARM64 Mach-O 路线，区分已核对事实、工程推断和必须通过的实验。结论是继续推进受限研究原型，同时把 ABI、内存和异常语义设为进入游戏适配前的硬门槛。现有证据尚不足以确认通用兼容层可以保持轻量，或最终帧率会超过成熟的 Wine 方案。

这是一轮独立反方审查。下面的反例并不证明静态翻译不可行；它们指出哪些关键假设一旦失败，就需要更换实现路线、缩小目标游戏范围，或接受更大的运行时。除特别注明外，实验是待执行的验收要求，不能当作已通过结果。

## 审查结果

| 核心假设 | 当前判断 | 对项目的影响 |
|---|---|---|
| ARM64 Mach-O 可以直接使用 ARM64 Wine 或 ARM64EC DLL | 不成立，需要明确 ABI 和装载边界 | 先选运行时边界，再扩展 API |
| guest 代码地址可统一替换为 host 指针 | 不成立 | 必须保留 guest 地址身份和双向映射 |
| 转成 LLVM IR 就能保留 Windows 异常语义 | 不成立 | 异常和状态重建决定优化边界 |
| 普通 ARM 内存访问足够运行 x86 多线程程序 | 不成立 | 编译器和硬件两层都要保留语义 |
| 当前机器具备新 ARM Wine 的所有条件 | 不成立 | 新平台能力不能作为现有实验的前提 |
| Remill 是可直接链接的完整跨架构运行器 | 不成立 | 需要单独验证目标布局、内存、调用及代码质量 |
| DXMT 原生 dylib 构建消除了 Windows 图形集成成本 | 不成立 | COM 对象、WSI、回调和窗口仍需桥接 |
| 当前循环微基准能支持游戏性能预期 | 不成立 | 首先建立难以代数消除的真实工作负载 |

## 一 运行时 ABI 必须先确定

**已核对事实。** Windows ARM64EC 是为 x64 互操作设计的特定 ABI，包含寄存器约束、入口出口 thunk 和间接调用检查机制。它不是 Darwin ARM64 ABI 的别名；其文档甚至约束了可以使用哪些 ARM 寄存器及其到 x64 `CONTEXT` 的映射。普通 ARM64 Mach-O 不会因为指令集相同就自动满足这些约束。[Microsoft ARM64EC ABI](https://learn.microsoft.com/en-us/windows/arm/arm64ec-abi)

**反例。** 把 IAT 中的函数地址直接改成一个 ARM64EC PE 导出地址，既没有解决 PE 模块装载，也没有解决 guest 调用栈、变参、结构体返回、错误码和反向回调。即使 `GetCurrentProcessId` 成功，也无法推出 `EnumWindows` 的 guest 回调或 COM 虚函数调用正确。

**最便宜的实验。** 在不接入图形的情况下，用自制 PE 调用一个原生测试库，再由测试库同步及异步回调 PE 函数。参数至少包含六个整数、混合浮点、结构体返回和函数指针；记录线程身份、TLS/LastError 和栈对齐。两种候选边界分别评估：AOT 内部使用 Darwin ABI、所有外部接口显式 thunk；或 AOT 作为 Wine/ARM64EC 的受控执行后端。不能混用两者的“已支持”能力。

**决策门槛。** 跨边界往返应有状态校验和每次调用成本。无法明确边界时，暂停扩展几十个 WinAPI。若复用 Wine 必须携带其服务进程、装载器、线程及对象模型，接受它为运行时基线，不再把“薄 shim”当成已经实现的约束。

## 二 guest 地址身份与原生调用优化可能冲突

**已核对事实。** PE 的 RVA、装载 VA、导入、重定位和异常表描述的是原二进制地址空间。它们与重新生成的 ARM 指令位置没有一一相同的布局。[Microsoft PE 格式](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

**反例。** 程序可以比较函数指针、把函数地址加偏移、通过 vtable 调用、读取返回地址、保存栈后稍后恢复，或跳到同一函数内的基本块。把每个“识别到的函数”直接变成 C 函数并用 native call/return 替代，并不能同时保持这些行为。只修 `.reloc` 也不能识别所有藏在数据或计算中的代码指针。

**最便宜的实验。** 制作一个含尾调用、递归、switch 跳转表、函数指针数组及返回地址观测的 PE。改变装载基址和 ARM 函数布局后，验证 guest 可见地址、分支结果和返回地址仍一致。对于 guest 程序可读的原代码，明确保留原字节的只读视图；host 执行地址保存在另一个映射域。

**决策门槛。** 只有能证明某个函数不观察 guest 栈、代码地址及异常状态时，才把它提升为更激进的原生 ABI 函数。其余路径保留 guest 状态和 guest 返回地址，或进入经过验证的分派器。地图中缺失的地址必须报错或显式回退，不能猜测最近函数入口。

## 三 精确异常会限制寄存器和内存优化

**已核对事实。** Windows x64 展开规则依赖 `.pdata`、`.xdata`、函数中的指令偏移及非易失寄存器保存位置。语言相关处理器还附带自己的状态。macOS 的本机展开信息不能直接解释这些 x86 描述。[Microsoft x64 异常处理](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64)

**反例。** LLVM 将多个 guest 指令合并、移动内存访问或消除中间寄存器状态后，发生越界访问时可能找不到正确 guest RIP、RSP 和寄存器值。异常处理器可能修改 `CONTEXT` 后继续运行；仅能打印 backtrace 或退出进程不算支持 SEH。host 回调进入 guest 后抛出的 C++ 异常，也不能未经设计地穿越两套栈。

**最便宜的实验。** 两类样本即可揭示主要缺口：一类跨三层 guest 调用抛异常并验证析构顺序；一类触发受控访问异常，核对 guest fault 地址及上下文，然后恢复到指定 guest 地址。再加入一次 host→guest 回调边界，记录哪些异常允许跨越、哪些必须就地转换。

**决策门槛。** 为可能 fault 的位置建立 host PC 到 guest PC 与状态重建映射，或先明确只支持无需该机制的样本。状态重建失败时禁止激进优化该区域。不能以“游戏没有主动抛 C++ 异常”推断整个进程不需要展开、guard page 或其他异常路径。

## 四 x86 内存语义同时受到编译器和 ARM 硬件影响

**已核对事实。** Remill 将 guest 内存访问、屏障和原子区域作为下游需要实现的语义边界；FEX 的 ARM 后端具有专门的 TSO 访存路径及屏障处理。这些都说明内存兼容不是普通寄存器翻译的自然副产品。[Remill 设计](https://github.com/lifting-bits/remill/blob/56918a8c2554088e93389e97d292f4035286506c/docs/DESIGN.md)、[FEX 内存后端](https://github.com/FEX-Emu/FEX/blob/1c4f04b71a4d33091183fd7e1a2c09e6823d27fd/FEXCore/Source/Interface/Core/JIT/MemoryOps.cpp)

**工程推断。** 将 guest 访存朴素生成为 C 指针读写，除了硬件内存序问题，还可能引入 C/LLVM 的数据竞争、对齐和别名假设；`volatile` 不是完整的跨线程同步模型。即使硬件支持 TSO 模式，也不能纠正编译器此前已经进行的非法重排。给每次访问加最强屏障虽然保守，却可能吃掉 AOT 的性能收益。

**最便宜的实验。** 用手写 x86 字节构造 message-passing、store-buffering、锁前缀原子和未对齐访问测试，避免参考实现自身落入 C 数据竞争未定义行为。message-passing 中“观察到发布标志却看不到其前面的数据写入”应按 guest 规则禁止；store-buffering 的双零结果在 x86 TSO 下本来就可能合法，不能把所有弱结果都判错。并行测量相同 load/store 热循环在保守屏障、经过证明的屏障消除和可用硬件模式下的成本。

**决策门槛。** 每次优化要说明被保留的 guest 内存语义。不能通过关闭 TSO 兼容或忽略罕见结果达到性能门槛；也不能仅凭一次长时间未观察到错误就宣称语义证明完成。

## 五 4 KiB 页与新 macOS 能力是条件依赖

**已核对事实。** Wine 开发者在 2026 年 8 月说明，新 ARM macOS 路线涉及 x18、4 KiB 页、低地址空间和 TSO 能力，且受 OS、SDK 与 entitlement 条件约束。同一线程的 9 月讨论显示免费账户实际获取 entitlement 存在障碍，不能将公告中的账户可用性视为本项目已验证能力。本机记录为 macOS 26.3.1、SDK 15.2，尚不满足该新路径的完整条件。[Wine 开发者原始说明与后续讨论](https://list.winehq.org/hyperkitty/list/wine-devel@list.winehq.org/thread/CKG5CEN2BE5VRXZ7O7NX4YUSBH3247WH/)

**反例。** 同一 16 KiB host 页内的两个 4 KiB guest 页可能分别是只读和可写，或其中一个是 guard page。对整个 host 页直接应用一种权限会改变程序行为。把 x86 指令静态翻译成 ARM 并不会消除 `VirtualProtect`、堆分配器、栈探测对这些语义的依赖。

**最便宜的实验。** 独立于完整游戏，验证保留/提交、相邻 4 KiB 权限切换、guard-page 首次访问、低地址映射以及新线程平台状态初始化。当前系统先做支持矩阵和软件模型；具备合适 OS/SDK/授权后再验证平台快速路径。

**决策门槛。** 默认环境只承诺已验证的能力。若选择软件 guest 页模型，必须把逐次检查、fault 转发及 API 指针桥的开销纳入基准。若选择平台特定能力，应把最低环境和签名条件写成真实部署要求；不得用关闭系统安全保护作为项目的默认解决办法。

## 六 Remill 的语义可复用性不等于已获得高性能重编译器

**已核对事实。** Remill 负责指令提升；其设计将内存和部分控制流实现留给下游。`State.h` 显式要求跨架构布局稳定，并警告仅改变 LLVM `DataLayout` 不能保证原先类型布局断言仍成立。[Remill State 约束](https://github.com/lifting-bits/remill/blob/56918a8c2554088e93389e97d292f4035286506c/include/remill/Arch/X86/Runtime/State.h)

**反例。** 一个函数可以成功生成 ARM 目标文件，却因 guest State 偏移、x87 表示、内存 helper ABI 或调用约定错误而产生错误结果；也可能完全正确，但每条指令都读写大 `State`、调用 helper，导致比成熟 DBT 更慢。当前自制 C 提升器能够把循环优化掉，不能证明真实 Remill IR 也能消除这些开销。

**最便宜的实验。** 固定 Remill 和 LLVM 版本，先提升三种自制 x86 函数：带数据依赖的整数混合计算、数组内存循环、128 位向量计算。为 guest State 字段偏移和 helper 签名建立独立检查；分别查看未优化/优化 IR、ARM 反汇编、残余 helper 次数和栈溢出。参考程序从原始 guest 字节执行获得，而不是重写同一份语义公式。

**决策门槛。** 首先满足结果一致和布局可解释，再判断 AOT 的函数隔离、状态标量化是否有效。若简单内存循环仍由 helper 或状态溢出主导，应先优化此路径或更换后端，不要据“LLVM 支持 ARM64”开始整游戏接入。

## 七 DXMT 原生库仍需要对象和窗口边界

**已核对事实。** 当前 DXMT 文档明确提供 Mach-O dylib 的 Native Build。与此同时，`dxgi_factory.cpp` 的 swapchain 路径仍处理 COM 接口、`HWND` 以及窗口系统接口。因此原生编译能力是有用的起点，但不是现成的 guest D3D ABI 桥。[DXMT 构建文档](https://github.com/3Shain/dxmt/blob/d162ea44a31fbf9089ea09977337f0beb30bd082/docs/DEVELOPMENT.md)、[DXGI factory 实现](https://github.com/3Shain/dxmt/blob/d162ea44a31fbf9089ea09977337f0beb30bd082/src/dxgi/dxgi_factory.cpp)

**反例。** guest 获得一个 host COM 对象指针后，从 vtable 读取的函数地址属于哪套地址域、调用约定与对象布局，必须有统一答案。只实现 `D3D11CreateDevice` 的导入 thunk 并不足以支持其后数百次虚函数调用。窗口 resize、资源引用计数及多线程 immediate/deferred context 还会跨越 CPU 与图形生命周期。

**最便宜的实验。** 首先在原生 ARM 程序中验证选定 DXMT 构建能创建 device、离屏渲染三角形并回读像素；随后用 guest PE 经过桥接完成同一流程。最后加入窗口与 swapchain、resize 和一次资源销毁压力测试。离屏成功并不自动等于桌面 WSI 成功，应分别记录。

**决策门槛。** 为 guest 提供可解释的 COM 代理对象和方法桥，或证明所选对象表示允许直接调用；测量每 draw/dispatch 的桥接成本。如果需要大量逐游戏补丁才能跨越对象边界，应改用成熟 Wine 图形集成作为基线，不把这部分成本归因于 CPU 静态翻译。

## 八 性能优势要排除样例结构和覆盖率偏差

**本地事实。** 当前微基准包含极短的整数加法以及可被 LLVM 转成闭式计算的求和循环。它们证明这些输入字节可以得到正确且高效的局部 ARM 代码。样本没有一般 guest 内存、异常、跨模块调用或图形工作负载；原始 x86 在 Mach-O harness 中经 Rosetta 执行，也不等于运行了完整 Windows PE 进程。

**反例。** 在真实游戏中，AOT 代码膨胀、间接分派、状态保存、同步、图形驱动或 shader 编译都可能占主导。即使 CPU 计算耗时减半，GPU 已是瓶颈时帧率也可能几乎不变。静态覆盖的分母也不能使用“解码出的函数”：漏掉的目标原本就不会进入该分母。加载屏幕的单次动态 trace 不能代表读档、异常、不同关卡和新 DLL。

**最便宜的实验。** 下一组至少包含不可轻易代数消除的数组 checksum、间接调用表、SIMD 内积及带同步的生产者消费者。相同输入同时运行原始 guest 字节、AOT 和源码原生版本，验证结果后比较 wall time、代码体积和 helper/回退比例。进入图形阶段时固定相同后端与画质，分开测量冷启动、暖缓存、CPU frame time、GPU frame time 和尾部帧时间。

**决策门槛。** 先要求代表性 CPU 工作负载得到可重复收益，再承诺某个游戏的目标。选择不含 CPU JIT 的初始目标；脚本解释器并不自动等于 JIT，应具体核对运行时。若确需动态代码，明确采用兼容层的动态回退或拒绝该目标，不把“无 Rosetta”写成“无任何运行时翻译”。源码原生、Wine+Rosetta、ARM Wine+FEX、定制 AOT 应各自标明测试环境，不能混用其结果。

## 继续开发前的顺序调整

最优先的不是增加导入 API 数量，而是完成两个彼此独立的验证闭环：真实 lifter 的语义与代码质量，以及 guest 地址空间到 host API 的往返调用。它们通过后再开展线程/页语义、异常和图形桥接。原生 DXMT 的离屏验证可以独立进行，但不能提前宣称它已经与 PE AOT 产物集成。

第一阶段允许把未知指令、未知间接目标和不支持的 PE 目录明确拒绝。进入游戏阶段前，需要把这些拒绝变成版本化支持清单和可复现失败证据。开发进度按能力验收推进，用固定目标实验判断是否值得继续投入；不能由当前原型推定通用、高性能Steam游戏转换器必然可交付。

最终 Go 条件应同时包括：选定输入的语义测试通过、所有部署依赖可取得、目标覆盖率可解释、同条件性能收益超过测量噪声，并且维护成本可接受。任何一项缺失，都只支持继续实验，不支持宣布方案已完成。
